# Folio V1 API implementation baseline (#9)

## Runtime and intended ownership
The API is a NestJS modular monolith. Its active system routes are `/v1/health`, `/v1/ready` and `/v1/system/capabilities`. The authenticated self-service routes `GET/PATCH /v1/me/onboarding`, `GET /v1/me/sessions` and `DELETE /v1/me/sessions/:sessionId` verify the database-backed principal on each request. The HTTPS browser login/CSRF/logout endpoints exist but are disabled unless `FOLIO_WEB_AUTH_MODE=direct-tls-only` and genuine direct TLS plus exact-origin and secret policies are configured. OpenAPI docs are at `/openapi`, JSON at `/openapi-json`, snapshot at `docs/api/openapi.v1.json`. Capabilities deliberately remain `available: false` until each catalog/reader feature is implemented. No mock users or catalog records are served.

- Every request receives a server-generated `x-request-id`, independent of untrusted incoming headers; the response error includes the same UUID.
- `@folio/contracts` contains cross-platform Zod validation and cursor/page/error schemas. The typed `fetchCapabilities` client can run on web/native/admin without Node-only Buffer use.
- Cursor pagination enforces bounded result size (1-50), a strict query shape and a canonical opaque cursor. Invalid and unknown cursors result in HTTP 400.
- An owner resource guard accepts a user context only when provided by trusted authentication middleware and denies absent or mismatched IDs. For the implemented self-service routes, `VerifiedSelfSessionGuard` resolves a database-verified bearer OR the gated HttpOnly web session, never caller-supplied user IDs or admin roles. This does not imply all future domain routes are implemented.
- Liveness `/v1/health` checks the process only; `/v1/ready` independently checks PostgreSQL availability and returns 503 without a configured/reachable database. A 200 liveness is not proof of database or job queue readiness. Full worker readiness is separately scoped.
- Contracts and error formats are tested over a real loopback HTTP listener. OpenAPI drift is blocked by `pnpm --filter @folio/server openapi:check` during `pnpm check`. Snapshot updates use `pnpm --filter @folio/server openapi:write`, followed by review and test.

## Future module boundaries
Auth/permissions, catalog/rights, reading/progress, social/invites, storage, import/export, audit and jobs share **one API** and **one DB**. No independent microservices, Redis, scraping, AI translation/TTS, or active provider integration is required for V1.

This baseline does not claim complete admin RBAC/MFA, public verified-email registration and reset, fully operational catalog/reader APIs, universal input/rate limits, content sanitization or production readiness; those remain in their V1 issues. Implemented self-service routes reject requests without verified ownership, and private catalog/book resources are not publicly exposed.

## Moduler HTTP sinirlari (#9, 10 Ekim 2026)
`apps/server/src/main.ts` sadece Nest uygulama bootstrap, `AppModule`, global request-id middleware, exception filter ve OpenAPI kurulumunu bir araya getirir. `modules/system/system.module.ts` saglik, DB readiness ve mevcut ozellik durumu API endpointlerini tasir. `common/http.ts` fail-closed kullanici kaynak sahipligi guard'i, normalized hata cevabi ve sunucunun urettigi request-id katmanini tanimlar. Yeni katalog, kullanici, reader veya admin endpointleri bagimsiz Nest modullerine, ilgili yetki kontrolleri tamamlandiginda eklenecektir. Bos ozellik modulleri ya da sahte calisan API'ler eklenmedi.

`owner-http.spec.ts`, SADECE TEST modulu icinde `@UseGuards(UserOwnershipGuard)` ile gercek ephemeral HTTP endpoint kurar. Gercek header icindeki `x-user-id` ya da `x-request-id` guvenilir auth olamaz: kimliksiz 401, baska principal 403, test katmani tarafindan onayli ayni principal 200; her reddin response `x-request-id` ile hata UUID'si birebirdir. Bu endpoint production AppModule icinde tanimli degildir. `http.spec.ts` ayrica paylasilan `fetchCapabilities()` istemcisinin gercek NestJS endpointinden donen Zod verisiyle ayni sonucu aldigini dogrular. OpenAPI snapshot degismedi.

Bu #9 icin mimari ve HTTP test iyilestirmesidir. Gercek admin oturumu/MFA (#30/#43), DB audit olaylarina istege ozgu request-id baglama ve butun kaynak rotalarinda hak/ownership enforcement sonraki islerin kabul kosuludur. Yetkisiz private endpoint eklenmedigi icin #9 su asamada otomatik tamamlandi sayilmaz.


## Trusted HTTP request ID correlation for secure Web sign-in (#9 partial)

The existing `RequestIdMiddleware` generates a new UUID and writes the same ID to `x-request-id` and `request.requestId`; incoming `x-request-id`, `x-user-id`, `x-admin-role` and proxy headers are not trusted. The opt-in direct-TLS `POST /v1/auth/web/login` now passes the server-generated ID through `WebAuthDb.login` into the PostgreSQL `signInVerifiedAccount` transaction. Its `auth.session.created` audit row stores the UUID in `audit_events.request_id` alongside the session record, never as a token, password, user-chosen role or email. Internal database calls with no associated HTTP request continue to omit the ID. A supplied malformed programmatic ID is rejected by the database function before any account lookup, and the HTTP code never reads the caller's request-id header.

Web logout already passes the trusted `request.requestId` to the owner-verified `revokeVerifiedDeviceSession` transaction. The existing genuine ephemeral direct-TLS NestJS and Folio-only `folio_test` PostgreSQL smoke test now confirms the unique login/logout `x-request-id` response headers equal their respective creation/revocation audit UUIDs, and a spoofed client header cannot be selected. Invalid credentials, CSRF, TLS or rate-admission failures must not generate a session audit. No endpoint, cookie policy or DB migration is changed.

This fixes only the **Web session-create request-audit propagation** part of #9, not the full #9 DoD. Admin RBAC audit propagation, complete contract parity for future domains, native device QA, production security gate #7, and the remainder of #30 are not accepted or marked completed. The `pnpm check` and genuine HTTPS/PostgreSQL smoke suite in GitHub Actions provide development evidence while Desktop Commander `mehmet` is unavailable. Nothing is deployed.

The companion `web-self-https-smoke` now verifies the **same HTTP header ↔ PostgreSQL audit UUID equality** for verified Web login, CSRF-protected onboarding PATCH, and owner-only device DELETE in one genuine transient HTTPS session. It injects forged request-id, user-id and role headers and checks three distinct server-generated trace IDs and no extra mutation audits after 400/401/403/404/409 rejections. This tests existing route propagation rather than enabling any new endpoints.
