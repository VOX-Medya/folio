# Folio V1 API implementation baseline (#9)

## Runtime and intended ownership
The API is a NestJS modular monolith. Its active system routes are `/v1/health`, `/v1/ready` and `/v1/system/capabilities`. The authenticated self-service routes `GET/PATCH /v1/me/onboarding`, `GET /v1/me/sessions` and `DELETE /v1/me/sessions/:sessionId` verify the database-backed principal on each request. The HTTPS browser login/CSRF/logout endpoints exist but are disabled unless `FOLIO_WEB_AUTH_MODE=direct-tls-only` and genuine direct TLS plus exact-origin and secret policies are configured. OpenAPI docs are at `/openapi`, JSON at `/openapi-json`, snapshot at `docs/api/openapi.v1.json`. Capabilities deliberately remain `available: false` until each catalog/reader feature is implemented. No mock users or catalog records are served.

- Every request receives a server-generated `x-request-id`, independent of untrusted incoming headers; the response error includes the same UUID.
- `@folio/contracts` contains cross-platform Zod validation and cursor/page/error schemas. The typed `fetchCapabilities` client can run on web/native/admin without Node-only Buffer use.
- Cursor pagination enforces bounded result size (1-50), a strict query shape and a canonical opaque cursor. Invalid and unknown cursors result in HTTP 400.
- An owner resource guard accepts a user context only when provided by trusted authentication middleware and denies absent or mismatched IDs. For the implemented self-service routes, `VerifiedSelfSessionGuard` resolves a database-verified bearer OR the gated HttpOnly web session, never caller-supplied user IDs or admin roles. This does not imply all future domain routes are implemented.
- Liveness `/v1/health` checks the process only; `/v1/ready` independently checks PostgreSQL availability and returns 503 without a configured/reachable database. A 200 liveness is not proof of database or job queue readiness. Full worker readiness is separately scoped.
- Contracts and error formats are tested over a real loopback HTTP listener. OpenAPI drift is blocked by `pnpm --filter @folio/server openapi:check` during `pnpm check`. Snapshot updates use `pnpm --filter @folio/server openapi:write`, followed by review and test.

## Future module boundaries
Auth/permissions, catalog/rights, reading/progress, social/invites, storage, import/export, audit and jobs share **one API** and **one DB**. No independent microservices, Redis, scraping, AI translation/TTS, or active provider integration is required for V1.

This baseline does not claim complete admin RBAC/MFA, public verified-email registration and reset, fully operational catalog/reader APIs, universal input/rate limits, content sanitization or production readiness; those remain in their V1 issues. Implemented self-service routes reject requests without verified ownership, and private catalog/book resources are not publicly exposed.

## Trusted HTTP request ID correlation for secure Web sign-in (#9 partial)

The existing `RequestIdMiddleware` generates a new UUID and writes the same ID to `x-request-id` and `request.requestId`; incoming `x-request-id`, `x-user-id`, `x-admin-role` and proxy headers are not trusted. The opt-in direct-TLS `POST /v1/auth/web/login` now passes the server-generated ID through `WebAuthDb.login` into the PostgreSQL `signInVerifiedAccount` transaction. Its `auth.session.created` audit row stores the UUID in `audit_events.request_id` alongside the session record, never as a token, password, user-chosen role or email. Internal database calls with no associated HTTP request continue to omit the ID. A supplied malformed programmatic ID is rejected by the database function before any account lookup, and the HTTP code never reads the caller's request-id header.

Web logout already passes the trusted `request.requestId` to the owner-verified `revokeVerifiedDeviceSession` transaction. The existing genuine ephemeral direct-TLS NestJS and Folio-only `folio_test` PostgreSQL smoke test now confirms the unique login/logout `x-request-id` response headers equal their respective creation/revocation audit UUIDs, and a spoofed client header cannot be selected. Invalid credentials, CSRF, TLS or rate-admission failures must not generate a session audit. No endpoint, cookie policy or DB migration is changed.

This fixes only the **Web session-create request-audit propagation** part of #9, not the full #9 DoD. Admin RBAC audit propagation, complete contract parity for future domains, native device QA, production security gate #7, and the remainder of #30 are not accepted or marked completed. The `pnpm check` and genuine HTTPS/PostgreSQL smoke suite in GitHub Actions provide development evidence while Desktop Commander `mehmet` is unavailable. Nothing is deployed.

The companion `web-self-https-smoke` now verifies the **same HTTP header ↔ PostgreSQL audit UUID equality** for verified Web login, CSRF-protected onboarding PATCH, and owner-only device DELETE in one genuine transient HTTPS session. It injects forged request-id, user-id and role headers and checks three distinct server-generated trace IDs and no extra mutation audits after 400/401/403/404/409 rejections. This tests existing route propagation rather than enabling any new endpoints.


## Shared system clients and transport fail-closed policy (#9 partial)

Previously `@folio/contracts.fetchCapabilities` accepted an arbitrary base URL and used a default GET with browser credentials/redirect/cache policy left unspecified. Health `/v1/health` and database readiness `/v1/ready` were not represented by an equivalent typed, cross-platform API client. That allowed frontend callers to accidentally accept stale status or follow redirects when they were supposed to be querying Folio.

The existing `fetchCapabilities(baseUrl, query, fetcher)` API is preserved but now implemented in `packages/contracts/src/system-client.ts` alongside `fetchSystemHealth`, `fetchSystemReadiness` and the typed `SystemHttpError(status, code, requestId)`. All three public, unauthenticated GETs first require a validated **HTTPS origin**, allowing cleartext HTTP only for explicit loopback development `localhost`/`127.0.0.1`/IPv6 loopback as previously supported by `verifiedApiOrigin`. Embedded username/password, path/query/fragment, other schemes and remote cleartext HTTP are rejected *before network*. They use `credentials:'omit'`, `redirect:'error'`, `cache:'no-store'`, `referrerPolicy:'no-referrer'` and `accept:application/json`. A 200 response must satisfy the exact strict shared Zod DTO; invalid JSON, wrong 2xx status, unexpected/expanded payload or malformed error is an explicit typed failure, never a ready/available assumption. Normalized 4xx/5xx errors retain only the server-defined error code, numeric status and safe UUID request correlation, not free-form server messages or credentials. The cursor query is parsed before network and percent-encoded canonically. No admin or user credentials are ever supplied by this public client.

NestJS readiness now parses the shared `readinessResponseSchema` `{status:'ready'}`; its OpenAPI JSON shape and actual route semantics do not change. Existing live HTTP checks compare direct responses against new typed `fetchSystemHealth` and `fetchSystemReadiness` calls. Vitest negative tests cover remote HTTP, origin contamination, bad query, unknown fields, 204/503, response schema poisoning and no-cookie/no-redirect semantics. This is **partial #9** shared-client parity, not a proof of production admin authentication or a new readiness service; readiness still verifies DB only, not queue workers. Native and browser UI acceptance, admin RBAC/MFA and all business domain routes remain open. GitHub-hosted Ubuntu CI does not replace the unavailable Desktop Commander `mehmet` lab. No deployment.


## Server-side cache safety for system probes (#9 partial)

`GET /v1/health`, `GET /v1/ready` and `GET /v1/system/capabilities` now explicitly send `Cache-Control: no-store` in their successful responses. The global `ApiExceptionFilter` separately applies the same header on HTTP 400/503 errors for those exact system paths. Thus an intermediary or embedded browser cannot preserve a stale `ready` response during PostgreSQL failure or persist an old feature availability page; client-side `cache:'no-store'` is not the only line of defense. The pre-existing account and Web-cookie exception policy **remains** `Cache-Control: private, no-store`. No cache bypass, new endpoint, public user data or production configuration is introduced.

The real loopback NestJS `http.spec.ts` checks no-store on liveness 200, capabilities 200, invalid cursor/query 400, and readiness 200 or explicit DB-outage 503. These checks run within `pnpm check` along with the API snapshot parity test. This is not a security release approval, health success never implies queue readiness, and #9/#7 remain open pending their broader acceptance.

## Internal draft/catalog/rights audit trace preparation (#9 partial)

The existing internal-only `@folio/db` commands `createCanonicalAuthor`, `createCanonicalWork`, `submitRightsEvidence` and `reviewRightsEvidence` accept a new **optional final `requestId` argument**. It is parsed as a UUID before any database query or mutation; an invalid value fails without inserting a draft author/work, evidence or review. The successful command writes `audit_events.request_id` together with the parent row and its audit event in the **same PostgreSQL transaction**. When the command has no associated HTTP request (e.g. offline trusted CLI/worker), the ID stays SQL `NULL`, not a fabricated trace. Rights submissions always remain `pending`, and human-reviewed test fixtures do not create public distribution rights.

This argument is a **correlation value only**, not proof of authentication, admin role, MFA, trust in caller headers, or legal rights. Any future privileged NestJS route MUST supply only `RequestIdMiddleware`'s server-owned `request.requestId` after server-verified admin authentication + MFA + RBAC. It MUST NEVER accept `x-request-id`, `x-admin-role` or a body-selected actor as trusted. There is deliberately still **no real admin catalog/evidence/review HTTP route**; the API/OpenAPI exposure is unchanged. This is preparation for the #9/#12/#14/#30/#43 protected admin implementation, not fulfillment of its access-control DoD.

`packages/db/scripts/catalog-smoke.ts` and `rights-smoke.ts` run against isolated Folio `folio_test` PostgreSQL. They check exact UUID equality for author, work, evidence, approval and withdrawal audit events; preserve no-trace internal commands as `NULL`; and fail closed on malformed caller-provided trace before any state/audit write. No real content, privileges, accounts, migration, service, provider or production setting is added.

## Default-off admin TOTP HTTPS transport (#9/#30 partial)

`AdminTotpModule` adds three explicit `POST /v1/admin/mfa/totp/{enroll,confirm,verify}` paths to the NestJS modular monolith and versioned OpenAPI snapshot. They are **not available by default**: only `FOLIO_ADMIN_TOTP_HTTP_MODE=direct-tls-only`, actual app TLS and a configured 256-bit AES-GCM key can enable the routes. Proxy `X-Forwarded-Proto` does not count as TLS. A separate preflight guard rejects disabled routes with 404 and missing TLS/secrets with 503, before any credential or seed handling. Success and normalized API errors are always private/no-store with server-generated `x-request-id` independent of caller headers.

Browser `POST` uses the currently available strict HttpOnly web cookie, same Origin/Sec-Fetch-Site and the HMAC token from `GET /v1/auth/web/csrf`. The native transport uses one TLS Authorization bearer and **no Cookie or browser Origin**. The controller never accepts a body/query `userId`, actor role, factor clock or server key. `enroll` accepts no data and returns a single secret/10-minute expiry only to the verified session; `confirm` strictly accepts a six-digit code and returns 204, while `verify` strictly accepts a new unused six-digit code and returns a device-bound 15-minute proof (without any bearer in the response). The backend requires an active, email-verified account with an existing nonrevoked admin role. Normal login alone never grants the MFA role; the initial superadmin/bootstrap and real UI are not implemented.

Tests: `bash infra/lab.sh admin-totp-https-smoke` runs real ephemeral TLS sockets and fake-but-verified Folio-only Postgres users (not real users), negative Origin/CSRF/crossover/plain HTTP/spoofed headers, typed DTO and audit assertions; the earlier `admin-totp-smoke` tests actual encrypted factor, failed attempts and cross-device replay in PostgreSQL. This does not claim real native secure storage or production readiness. See `docs/46-ADMIN-TOTP-VERIFICATION.md` and the blockers in #7/#30/#43.

## Admin TOTP AES envelope key versions (#30 incremental)

Existing direct-TLS MFA endpoints remain disabled by default. Their private server encryption configuration now supports both the legacy `FOLIO_ADMIN_TOTP_KEY_HEX` (v1) and optionally a distinct `FOLIO_ADMIN_TOTP_V2_KEY_HEX`. `FOLIO_ADMIN_TOTP_ACTIVE_KEY_VERSION` defaults to `v1` for compatibility and can explicitly select `v2` only if the staged v2 key is valid; missing/identical active key config yields **503** with no secret fallback. Each factor is decrypted only with its persisted key version and version-bound AES-GCM AAD. New enrollments select the active version; old factor records are not rewritten by migration. Internal-only per-account rotation and DBA version-count checks require superadmin+current device MFA; **no production key-changing endpoint or CLI** has been added. See `docs/46-ADMIN-TOTP-VERIFICATION.md` for safe key provisioning, verification, rollback and human-approval blockers.

## Native bearer versus browser session boundary (#9/#30 partial)

The verified self-service guard now rejects `Origin` or `Sec-Fetch-Site` on native `Authorization: Bearer` requests **before** a session lookup, even if a valid device token is supplied. This prevents a browser from bypassing the intended server-owned HttpOnly cookie and exact-origin/HMAC-CSRF transport with an application bearer. The existing Web cookie flow still requires direct application TLS, exact permitted origin and CSRF for unsafe mutations. A native client without browser metadata continues to use its already-verified session; no user-owned data is exposed through the request or headers.

The unit regression checks absence of DB lookup and forged-principal clearance. The real `folio_test` HTTP onboarding smoke checks browser-metadata GET/PATCH are denied with normalized `401` request-ID correlation and private no-store, without changing any onboarding progress. This is a narrow transport isolation change, **not** a public auth rollout or TLS/native device release approval. The remaining #9/#30 acceptance criteria and #7 release security gate remain open.

## Opt-in MFA/RBAC admin canonical metadata search (#9/#12 partial)

Two **read-only** NestJS routes are added under `GET /v1/admin/catalog/{works,authors}`, accepting only required `q` (1-120 chars), optional integer `limit` (1-50, default 20), and optional UUID `cursor`. They return deterministic UUID-paged work title/language/publication status or canonical author name/sort name. The catalog matching engine includes alternate titles, author aliases and edition contributors; SQL wildcards in the caller query are escaped. No user/person search, private book bodies, full text, unpublished files, media URLs, or publication action is exposed. Draft metadata is deliberately admin-only and remains unpublished.

**Runtime fails closed by default:** `FOLIO_ADMIN_CATALOG_HTTP_MODE=direct-tls-only` must be explicitly set; any other value produces `404`. Even when opted in, the request must arrive over the genuine *application* TLS socket; a proxy `X-Forwarded-Proto` claim cannot enable the route. Only existing verified account sessions can pass the self-session guard. HTTPS Web callers use the existing Secure HttpOnly cookie, same-origin proof, and HMAC-CSRF boundary where relevant; native callers use an isolated Bearer credential with **no browser Origin/Sec-Fetch-Site**. There is no caller-provided actor, role, principal or MFA claim. The session token is used only inside the API and never returned.

Crucially, the actual PostgreSQL catalog SELECT is executed as the **callback of** `withVerifiedAdminPermission(db,bearer,'catalog:read',...)`. The callback and active email-verified account, unrevoked device, unexpired same-device MFA proof and nonrevoked persisted RBAC membership checks share one transaction with shared locks. Authentication alone or a role alone is insufficient; a revoked role/MFA cannot race the SELECT. Only work/author *metadata* is returned, validated against strict `@folio/contracts` DTOs. All 200/400/401/403/404/503 responses under this path are `Cache-Control: private, no-store`. No migration, admin grant/bootstrap, audit write or user content change occurs.

Development acceptance: `pnpm check` and `bash infra/lab.sh admin-catalog-https-smoke` exercise strict parameters and responses, ephemeral real TLS, isolated `folio_test`, default-off and forged TLS deny, valid synthetic role+MFA and negative ordinary/moderator/no-device-MFA cases, direct cookie origin and native bearer separation, optimistic revocation and expiry checks, author alias/work search, 1-50 UUID pages, literal SQL wildcard, uncached normalized errors, and OpenAPI drift check. The test-only role/MFA fixtures are never a first-superadmin provisioning flow. Browser HTTPS UI/native device QA, complete admin CRUD, approval-backed publication/rights, real key custody and the #7 release security gate **remain open**. This is NOT permission for live deployment.

## Verified administrator canonical DRAFT creation (partial #9/#12/#22)

POST `/v1/admin/catalog/authors` and POST `/v1/admin/catalog/works` add **audited, unpublished** author/work metadata to the Nest modular monolith. Both are explicitly **disabled by default**, independently of the existing read API. Operators must enable **both** `FOLIO_ADMIN_CATALOG_HTTP_MODE=direct-tls-only` and `FOLIO_ADMIN_CATALOG_WRITE_MODE=direct-tls-only`; changing read-only access never implicitly enables writes. Both guards require actual application-socket TLS, not a client-supplied forwarded protocol. All responses, including 400/401/403/404/409/503, are private no-store.

These endpoints accept only the strict shared `authorCreateSchema` or `workCreateSchema` body and **no query fields**. Unsupported `userId`, `actorId`, `role`, owner, publication status, arbitrary text and rights fields are rejected. Author: canonical name, sort name, aliases and optional source-scoped external IDs. Work: original title/language, at least one real author, optional translated titles, editions, ISBN-like identifiers and contributors. New work, every edition and any content remain strictly **draft**; no source text, public catalog publish action, provider call or private user book access is implemented. Successful 201 responses return only canonical IDs and a literal `draft` status for works. Invalid relationship references return a sanitized 400, duplicate external IDs a sanitized 409, without database/query details.

The two public HTTP methods call only `createVerifiedAdminDraftAuthor` / `createVerifiedAdminDraftWork` in `@folio/db`. The actor is **derived exclusively from the persisted, current verified admin transaction**, which holds locks on the email-verified account, unrevoked session, same-device current MFA and persisted `catalog:edit` membership. The draft rows, all nested children and immutable `author.create` / `work.create` audit event with the **middleware-generated request UUID** are written in **the same PostgreSQL transaction**. A failed nested FK, unique external ID or audit abort rolls back all changes. Existing internal CLI/import `createCanonicalAuthor/Work` methods retain their trusted-actor APIs, but share the same insertion core; no authenticated HTTP route can supply a trusted actor itself.

The Web transport requires same-origin TLS HttpOnly session cookie and server-issued HMAC-CSRF header on POST; native transport has a standalone verified bearer and **cannot** present browser Origin/Sec-Fetch-Site or mixed cookie credentials. The read-only administrator can search but **cannot** create. Real `folio_test` + ephemeral HTTPS smoke includes forged role/user/request headers, read-only/moderator/normal/other-device/no-MFA denials, malformed strict inputs and query fields, correct 201 and audit correlation, author alias/ID and multilingual work with editions, duplicate-ID 409 and partially inserted invalid contributor 400 rollback, cookie CSRF missing/forged/cross-site, expired MFA/revoked role, two independent rollout flags and OpenAPI. Unit contracts and `pnpm check` test the schemas and snapshot. Synthetic lab factors/roles are never a real admin bootstrap. Actual admin editing UI, rights QA/publish, rate/lifecycle policy, native-device testing and the #7 production security gate **remain open**. No live rollout.

## Same-snapshot canonical work and author details (partial #9/#12)

The existing default-off direct-application-TLS admin **READ** flag, `FOLIO_ADMIN_CATALOG_HTTP_MODE=direct-tls-only`, also gates `GET /v1/admin/catalog/works/:workId` and `GET /v1/admin/catalog/authors/:authorId`. The independent catalog POST/write flag is **not required** for read-only detail and enabling it does **not** grant read privilege. Both routes require the current verified session plus the **same-device MFA** proof and persisted nonrevoked `catalog:read` permission, using `withVerifiedAdminPermission(..., {isolationLevel:'repeatable read'})`. The authorization SELECTs/locks and all nested work/author relation SELECTs are performed in **one PostgreSQL REPEATABLE READ transaction**. There is no public detail, user-search or unguarded second database call; malformed UUID/query returns 400, missing UUID returns 404 **only after authorization**, and unauthorized account/role/device requests return 401/403. For security, the authenticated transaction performs `FOR SHARE` locks and is not declared `SET TRANSACTION READ ONLY`; the detail callback itself runs only SELECTs. Existing internal `getCanonicalWorkDetails` retains DB-enforced read-only + REPEATABLE READ semantics.

The work detail API returns **only** the `work` UUID/title/original language/first-publication-year/publication status, ordered `authors` (ID, canonical name, role, order), `titles` (stable IDs, language, kind, title), and `editions` (stable IDs, language, label, publisher, status, ISBN/other identifiers and contributor references). The author detail API returns only canonical name/sort name, aliases with locale and source-scoped external IDs. Both contracts are strict and reject extraneous raw DB records, source text, private book bodies, encrypted objects, rights evidence, audit rows, session or personal user data. Work authors, titles, editions, identifiers and contributors are sorted by explicit order keys and UUID tie-breakers as in `@folio/db`, independent of physical insert order or query planner.

The existing `bash infra/lab.sh admin-catalog-https-smoke` verifies both paths on **real ephemeral HTTPS + dedicated Folio-only `folio_test` PostgreSQL**, with disabled feature 404, forged proxy TLS 503, forged identity headers and nonmember 401/403, read-only MFA editor success, editor secondary device without MFA 403, same-origin HttpOnly browser cookie success, cross-origin/mixed bearer denial, malformed path/query 400 and unknown UUID 404, actual newly created draft work/alias/edition/contributor relationships, deliberately out-of-order links, repeated deterministic response, no private content, role revocation and expired MFA denial, and OpenAPI. All errors/successes remain `Cache-Control: private, no-store`. This is **not** a rights-aware public listing, user bookshelf, revision/body stream or native device QA. #9/#12 stay open until the full API/UI acceptance criteria pass; #7 production security gate remains blocked.

## V1-00 #9 architecture acceptance boundary

The #9 deliverable is a **typed, versioned NestJS modular-monolith API foundation**, NOT completion of every domain's future API. The active production `AppModule` imports separate `system`, `account`, `auth/web`, `auth/admin-MFA` and `admin/catalog` modules. They all share the Nest app, `@folio/contracts`, PostgreSQL behind `@folio/db`, a server-owned `RequestIdMiddleware`, and normalized strict errors. No independent REST app, external job queue, mock people-search, content provider or fake public catalogue route is created.

Acceptance checklist for the **#9 architecture scope** (CI verification required before completion):
- **Versioned REST/OpenAPI + drift gate:** The real Nest `/openapi-json` contains only `/v1/*` routes, the actual registered methods, shared bearer and HttpOnly cookie security schemes. The checked-in `docs/api/openapi.v1.json` must exactly match regenerated output via `pnpm --filter @folio/server openapi:check` in `pnpm check`.
- **Contracts + status/error parity:** `@folio/contracts` exports strict Zod DTOs for health, DB readiness, capabilities, owner onboarding/sessions, verified Web transport and administrator MFA/catalog. `apps/server/src/http.spec.ts` and `apps/server/src/architecture-acceptance.spec.ts` exercise the **actual** Nest app over an ephemeral socket, including successful health + paginated disabled features and normalized errors. The same `@folio/contracts` schema types are reusable by Expo Web/native and the administration module. Full client UI parity for **not-yet-implemented** book/progress/social screens belongs to their respective tickets, not this architecture issue.
- **Pagination + request tracing:** `cursorQuerySchema` is bounded and unguessable where needed; malicious query/body/identity headers cannot grant owner or admin access. Server-issued UUID request IDs are sent in response and persist in appropriate real mutation audit events; a caller-provided `x-request-id` cannot select them.
- **Owner RBAC gates:** `UserOwnershipGuard`, `VerifiedSessionGuard` / `VerifiedSelfSessionGuard`, and real `/v1/me/*` owner-only DB-backed routes reject forged `x-user-id`, nonowner bearer, invalid/expired session, Web cross-site/CSRF/mixed transport. Administrative metadata is independently default-OFF + TLS + same-device MFA + DB-backed role-locked. Real Folio-only TLS/Postgres CI covers sessions and work/author metadata transactions.
- **Safety in incomplete features:** `/v1/system/capabilities` says disabled for unimplemented reader/public catalog/social functionality. New architecture test verifies that no `/v1/users`, `/v1/reader`, people search or test-only controller enters AppModule. Existing partial domain tickets remain OPEN.
- **Local CI and isolation:** `pnpm check` includes TS strict, ESLint, build, unit/HTTP contract tests, strict OpenAPI, Metro security. GitHub Ubuntu Actions also executes Folio-only PostgreSQL + ephemeral HTTPS E2E, Expo JS Web/Android/iOS exports, Playwright desktop viewport matrix, license scan and nondeploy Docker build. Native device QA (especially iOS Xcode) is not claimed. `mehmet` Desktop Commander access is quota-blocked; GitHub-hosted Ubuntu was explicitly approved as fallback.
- **Separate release gate:** #7 is STILL BLOCKED until audit has zero moderate/high/critical and native publishing acceptance, despite development CI success. Closing architecture #9 must **not** be treated as permission to deploy anything.

This chapter records the architectural acceptance surface and dependency separation; it does not claim the #7, #12, #21, #22, #29 or #30 full DoD.
