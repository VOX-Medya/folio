# #19 incoming package candidate identity claims (partial)

## Immutable boundary, unverified provenance

An authorized editor may record a claimed *incoming* UUID that is not yet a canonical work, together with a package UUID, claimed 64-hex manifest checksum, original title/language and optional claimed SHA-256 source digest. This does **NOT** upload, parse or verify a `tar.zst`, extract source text, approve rights, mark a real batch as staged or authorize import. The UI intentionally labels every result `provenanceVerified:false` and calls the candidate metadata a **CLAIM**. Source digest equality is an editorial clue and must never be treated as source-file verification, licensing, translation equivalence, author identity or publication permission.

An editor must first search/open a *real existing* canonical candidate work under MFA-protected admin. The new panel `AdminImportCandidateReviews` is shown only from this work detail. The editor copies a candidate from an existing **read-only `folioctl --dry-run` report** (or types the claimed fields). The POST never runs the import planner automatically or reads a local file. The server requires the claimed incoming original title+language to match the known canonical work exactly **or** the optional claimed source SHA-256 to equal an immutable source revision linked through a canonical edition. False claims without either evidence are rejected as 409. Both pieces of incoming information remain unverified until the actual manifest/source bytes are checked by the separate Folio engine.

## Storage and access control

Forward-only migration `0020_import_candidate_reviews.sql` adds `import_candidate_reviews`. There are no new relationships to import stages, catalog author records, rights, source revisions or publication. Existing canonical work FK is RESTRICT. `(package_id,incoming_work_id,candidate_work_id)` is unique, with UUID inequality and strict SHA/status/reviewer CHECK constraints. A package UUID with a different manifest checksum is rejected across any existing review case or stored `import_batches`. The proposal serializes on the same package advisory lock as staging. Identical repeats have `changed=false` and no extra audit; changed input for the same case is rejected. A changed canonical candidate metadata revision/status or newly matching source SHA invalidates the evidence digest; the proposer must explicitly renew the case, resetting decision to pending and incrementing the review revision.

Existing default-off **direct-application TLS** and independent READ/WRITE opt-in, exact-origin browser HMAC-CSRF, authenticated user+session, same-device MFA and PostgreSQL `catalog:read`/`catalog:edit` permissions apply to:
- `GET /v1/admin/catalog/works/:workId/import-reviews?cursor=UUID`: 20-item bounded UUID-paginated sanitised metadata. No account/reviewer identity, raw source, SHA, original rights proof, package bytes or session secrets. Existing candidate can be a DRAFT or published work, but is read-only and never changed by review.
- `POST /v1/admin/catalog/works/:workId/import-reviews`: strict claim fields only; no user-search ID, rights, autoMerge, sourceBody, public status or allowImport flags. A claimed incoming UUID already present as a canonical work is rejected. User input cannot mark provenance verified.
- `PATCH /v1/admin/catalog/works/:workId/import-reviews/:reviewId`: **different** MFA-verified editor must enter `expectedVersion`, `distinct|deferred` and 24–1200-character rationale. The proposer can never decide their own case. The PostgreSQL row lock serializes competing decisions; old versions, changed candidate evidence and duplicate verdicts give 409. Trusted before/after audit + actor + server request ID commit together with each actual mutation.

The web panel is TR/EN, responsive to 390px, accessible through labels and explicit two-click propose/decide, no optimistic delete or status. An ambiguous network response or 409 disables writes until explicit reload. "Distinct" means **editorial note only**. It does not change `previewPreparedCatalogImport.canStage`, permit `stagePreparedCatalogImport`, alter `resumeStagedCatalogMetadata`, merge work UUIDs or publish anything.

## Verification and missing DoD

Folio-only PostgreSQL `folio_test` + temporary direct HTTPS smoke simulates two independent real MFA editors, 200/201/400/403/409, authentic HMAC-CSRF/cookie, cross-origin and read-only denial, package-id/checksum reuse, same-request idempotence, simultaneous decisions, trusted audit, stale refresh, and **read-only preview still conflicts plus refused stage even after a distinct verdict**. Chrome Playwright explicitly uses mocked HTTPS API to exercise a 390px TR/EN form, conflict lock/manual reload and no retry. The generated OpenAPI snapshot, shared contracts and client tests are checked in CI. The UI API does **not** independently prove package bytes; native Android/iOS device tests, real browser joined to PostgreSQL in one E2E path, authenticated full-package apply/resume, author-author reviewer intake, complete manifest/file SHA verification in this UI, 25–50 whole-book assets/audio, human rights/publication approvals and safe resolved re-packaging are still unimplemented. #12 and #19 remain **OPEN**.

Independent release check stays blocked until its vulnerable dependencies are fixed; this review never authorizes a production build or deployment.
