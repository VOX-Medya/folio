# #19 Staged metadata import and read-only planning (partial)

## Implemented on 10 October 2026
The prepared local folder or `tar.zst` must pass the existing `folioctl` manifest, file SHA-256 and semantic block/relation verifier **before** a dry-run can reach the backend planner. `folioctl import <dir-or-archive> --dry-run [--report report.json]` is a read-only localhost-only development command. The command only connects to the explicitly provided Folio PostgreSQL port and database `folio_lab` or `folio_test`; the planner issues `SET TRANSACTION READ ONLY`, and it inserts no audit events, import batches, assets, rights records, authors, works or editions. Report output is exclusively created; existing report files are never silently overwritten. No authenticated apply/export CLI, Admin API or HTTP bypass exists.

`previewPreparedCatalogImport` operates on canonical authors/works/editions/revisions already in the database, keyed by stable supplied UUIDs and relationships. Existing same-ID identical author/work/edition => `noop`; different metadata for same ID => `conflict`. A same-title book or same-name author with a *different* UUID => `conflict` requiring manual investigation, **not** an automatic merge or guessed ISBN/title identity. New authors/works/editions => `create`. New content revisions and any supplied rights evidence => `deferred`, pending persistent raw-asset handling and human territory/usage approval. A reused package UUID with a different SHA-256 checksum is rejected. Prepared metadata has no inherent authority to publish.

`stagePreparedCatalogImport` (trusted **internal** DB function, not a public API) makes one persistent `import_batches` row keyed uniquely by package ID and stores individually hashed JSONB `import_items` snapshots. Replaying the same package/checksum is idempotent and must match every staged payload. It never alters the catalog. `resumeStagedCatalogMetadata` applies draft **catalog metadata only** in dependency order author -> work -> edition, using per-item PostgreSQL transactions, SHA-256 payload checks, short advisory locks, item checkpoints and sanitized audit events. Unchanged canonical identities produce explicit `noop`. Existing published work IDs or conflicting names/titles cannot be overwritten. A worker restart can resume using staged rows alone. `getStagedCatalogImportStatus` reports applied/pending/deferred counts. After metadata apply, the **batch stays `metadata_applied`**, not a completed/published import, with all content revisions `deferred_asset` and all rights evidence `deferred_review`. No source text, asset, audio or translation is published.

## Ubuntu real-DB integration evidence
`bash infra/lab.sh migrate` and `bash infra/lab.sh test-db` migrate the Folio-only databases without resets. `bash infra/lab.sh import-smoke` exclusively targets `folio_test` on the localhost Folio port and simulates 30 synthetic works: read-only preview 90 creates + 60 deferred with **zero** changes to author/work/edition/batch/item/audit counts; CLI folder/archive preview parity; 150 durable staged items with repeat package idempotency; 37 item checkpoint, new PostgreSQL pool simulating restart, 53 more metadata items completed; 30 authors+30 draft works+30 draft editions; 30 revisions still waiting for verified assets and 30 rights entries awaiting review. Re-run has zero new writes; wrong package checksum fails, foreign author/name or published-work mutation is blocked, and a tampered staged payload fails its internal SHA-256. Existing published synthetic fixture content is not overwritten. All test data is synthetic inside the **isolated** Folio test database.

## GH Actions regression: cross-scope validity and parallel checkpoint (#19)

`preparedImportSchema` now checks edition/revision language, rights-to-work hierarchy including references through editions and revisions, duplicate in-work authors and rejectable self-approved publication claims **before any database write**. Two separate PostgreSQL pools concurrently resume the same staged 4-work fixture. The isolated `folio_test` integration requires exactly 12 distinct applied metadata items and 12 per-item audit events, no processed-item overcount, and a final `metadata_applied` status that cannot be overwritten by a stale worker. All revisions and rights remain deferred. These checks are part of GitHub Actions' `import-smoke` step; no production import/public endpoint is enabled.

## SHA-256 canonical collision review, never automatic dedup (#12/#19 partial)

Prepared package `revisions[].source_sha256` is now mapped through each edition ID to its original work UUID for **review suggestions only**. The read-only `previewPreparedCatalogImport` uses a *single PostgreSQL REPEATABLE READ, READ ONLY snapshot*: matching immutable existing `content_revisions.raw_sha256` digests are followed through edition→work relationships. If a different canonical work UUID already holds **the exact same source bytes**, even if language/title/author metadata differs, the preview flags the new work `action:'conflict'`, `reason:'possible_source_sha256_match_requires_human_review'`. Candidates are stable sorted canonical UUIDs only, limited to 20 per planned row with `moreCandidates` indicator; no source body, private user data, author search or rights evidence leaves the DB. Same-title/same-language candidates continue to require manual review. Byte equality is evidence, not authority to equate translations, editions, persons, licensing or *different* works. If two **different works inside one package** reference the same source SHA, both are marked as ambiguous even if no database work exists.

Both CLI directory and tar.zst `--dry-run` retain strictly read-only semantics. `stagePreparedCatalogImport` refuses any conflicting digest/title/author plan without creating a batch, source, audit or work. `resumeStagedCatalogMetadata` validates persisted per-item SHA snapshots before any operation, rejects in-package shared source hashes across different works, and checks existing `content_revisions.raw_sha256` **again inside the candidate work's item transaction**, guarding metadata staging against an earlier preview that became stale. A late collision does not insert the conflicting work or apply its audit; previously applied dependency rows remain resumable, and the batch cannot claim successful complete publication.

The Folio-only `folio_test` `import-smoke` now creates a synthetic existing canonical work/edition/provenance/revision (never real text), submits an entirely different-title work with a byte-identical SHA, checks stable candidate UUID, `canStage=false` and no read/stage mutations. It verifies two different works in the same package with identical digests both require review, plus a post-staging new existing content revision that must veto creation before an irreversible duplicate work insert. **No reviewer-approved merge or mapping API exists** in this change. Approving distinct identities and re-packaging their separately verified metadata still requires a future authenticated reviewer workflow; this change deliberately does not invent an approval result or add auto-merge/publish flags. #12/#19 remain OPEN; content/rights and production gates unchanged.
