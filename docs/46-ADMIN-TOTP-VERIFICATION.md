# #30 Internal encrypted admin TOTP verifier (partial V1)

## Operational boundary
The V1 role and session prerequisite is the merged #43 RBAC/MFA gate. The internal `@folio/db` functions `beginAdminTotpEnrollment`, `confirmAdminTotpEnrollment`, and `verifyAdminTotpForSession` now have **explicitly gated** NestJS `/v1/admin/mfa/totp/{enroll,confirm,verify}` POST routes. The feature is **OFF by default** and returns 404; it requires `FOLIO_ADMIN_TOTP_HTTP_MODE=direct-tls-only`, a direct TLS **application socket** (never a spoofed `X-Forwarded-Proto`) and a privately configured 64-hex-character `FOLIO_ADMIN_TOTP_KEY_HEX`. Cookie callers must additionally enable existing `FOLIO_WEB_AUTH_MODE=direct-tls-only`, exact `FOLIO_WEB_AUTH_ORIGIN`, `FOLIO_WEB_CSRF_KEY_HEX` and present their verified HttpOnly cookie, matching Origin and HMAC-CSRF token. Native clients supply a single verified bearer without Cookie or browser Origin. Controllers derive `requestId` only from server `RequestIdMiddleware`; client actor/user IDs, code clock, crypto key and role headers are rejected. No real admin role management CRUD is exposed. Never accept an `x-admin-role`, query/body actor, user-provided clock or pasted encryption key. No role or first superadmin is created by TOTP enrollment. The server-only HTTPS endpoints have an ephemeral TLS/CSRF transport regression suite, but **production UI/secure user onboarding, factor recovery/rotation and independently reviewed initial superadmin bootstrap** remain blocked. The code cannot make an admin from an ordinary signed-in account without an existing, nonrevoked DB role.

## Secret protection and validation
- The forward-only `0014_admin_totp_credentials.sql` migration creates an empty `admin_totp_credentials` table; existing user/canonical/content rows are untouched. The pending seed is random 160 bits generated by Node CSPRNG, returned once to its authenticated enrolled-account operator (never logged); it is persisted ONLY as AES-256-GCM ciphertext, unique random 96-bit IV and 128-bit GCM tag. AAD `folio:admin-totp:v1:<user_uuid>` binds ciphertext to that account. Wrong key, swapped user or tampered cipher **fail closed**. DB stores an explicit `key_version` (`v1` or `v2`) and authenticates the account **and** key version in GCM associated data. Existing v1 records are unchanged by migration 0015. A **32-byte private server key** passed from secure configuration is mandatory; no default, test key or hardcoded production secret. No key is committed. Backups must include separately protected decryption-key recovery, but production key custody/recovery and retirement are NOT implemented. A new **internal-only, audited v1/v2 envelope rewrap** primitive can assist an approved deployment workflow; it is not a recovery endpoint.
- TOTP is RFC 6238 SHA-1, six digits, 30-second timestep, only current server timestep ±1 accepted. No client-provided date/time, algorithm or seed. Confirmation of a pending enrollment requires a correct TOTP within ten minutes, and **does not mint admin access**. A subsequent *different, previously unused* TOTP code is required for session step-up.
- `last_accepted_step` advances monotonically **inside the same transaction** under `FOR UPDATE` on the factor row. Identical code/time step cannot authorize a second request or device even on separate PostgreSQL pools. Code strings are not stored or audited; the encryption key and raw bearer never enter audit.
- Wrong codes increment a persistent `failed_attempts` counter (five failures block attempts for fifteen minutes), committed **before** a uniform denial is thrown. A cryptographic key/configuration outage does not silently create an MFA bypass. Expired enrollment cannot be confirmed. A pending/active seed cannot be silently replaced, except expired pending enrollment may begin anew.
- A real `verifyAdminTotpForSession` success creates/updates `admin_session_mfa` with the *same* user+session, `method='totp'`, `verified_at` and fifteen-minute expiry in that transaction. `withVerifiedAdminPermission` still checks active email-verified account, unrevoked device, current proof and exact DB role/permission; private book bodies remain forbidden even to superadmin.

## Explicitly gated NestJS transport (#30 partial)

`AdminTotpModule` is registered in the modular monolith but its factor routes return **404** until `FOLIO_ADMIN_TOTP_HTTP_MODE=direct-tls-only`. A genuine TLS socket and `FOLIO_ADMIN_TOTP_KEY_HEX` are prerequisites, otherwise **503**. All successful and error results set `Cache-Control: private, no-store`. The payloads are strict: enrollment takes no caller-selected user data, `confirm`/`verify` each accept exactly `{\"code\":\"000000\"}` with a six-digit string; enrollment returns a single `secretBase32, expiresAt` body only to the verified transport. Confirmation replies 204 without MFA privilege; verification replies a 15-minute `verified:true,expiresAt` proof state without exposing a token. Invalid/expired/replayed codes are generic 401; raw secrets are never included in audit.

The browser transport uses the **existing** `/v1/auth/web/csrf` HMAC-CSRF bootstrap and checks the same origin on POST; a bearer mixed with Cookie, cross-origin browser bearer, and forged `X-Forwarded-Proto` all fail closed. Native bearer is accepted only on actual app TLS; it is reverified inside the PostgreSQL factor transaction. `apps/server/src/scripts/admin-totp-https-smoke.ts` runs on an ephemeral self-signed HTTPS NestJS socket and isolated `folio_test` with synthetic verified accounts and role grants. It asserts 404 default, 503 missing key/plaintext-spoof, cookie CSRF/Origin negatives, no-client-owned actor fields, 200/204 typed responses, normal bearer+cookie separation, no-cache and audit secrecy, replay 401 and flag toggle. The HTTPS smoke exercises server behavior, **not** actual Android/iOS app storage or human factor enrollment.

## Versioned encryption key rollout (#30 partial, maintenance primitive)

`0015_admin_totp_key_versions.sql` is **forward only**. It permits `v1` and `v2` encryption labels without changing an existing record or MFA proof. No TOTP secret/backup/key is generated by migration. The existing `FOLIO_ADMIN_TOTP_KEY_HEX` remains the optional **v1** server key for reads while v1 records exist. The optional `FOLIO_ADMIN_TOTP_V2_KEY_HEX` is a **different** 32-byte hex key, never the same as v1. The new `FOLIO_ADMIN_TOTP_ACTIVE_KEY_VERSION` setting defaults to `v1`; `v2` may be selected only when the v2 key exists. The gated HTTPS MFA endpoints return 503 for an unavailable selected key, bad version or identical v1/v2 key. Both keys, when provided, allow previously stored v1 and new v2 factors to be decrypted by **their recorded version**. Never silently try alternate keys or a v1 fallback on v2 ciphertext.

Before *any* production deployment, a human operator must approve and privately escrow the new v2 key and recovery process. Safe intended procedure: (1) deploy and test the dual-read code with existing v1 key and staged distinct v2 key, (2) switch **all** application instances to active-write `v2`, keeping both read keys, (3) after verified human permission and authentic superadmin device MFA, use **internal-only** `rotateAdminTotpEnvelopeForUser(db, bearer, targetUserId, 'v1', 'v2', keyring, reason, trustedRequestId)` for individual records, (4) check `inspectAdminTotpKeyVersions(db,bearer)` and independently verify that `v1 === 0` across **all pending and active records**, and only then (5) after production change approval and documented tested backup/rollback, retire the old key. The safe procedure is **documentation only**; this change neither implements a production rotation CLI nor changes real keys/environment or initiates a rollout.

Each rewrap requires a real active verified admin account, live device-bound MFA and DB `users:support` permission (currently superadmin only). It locks the factor `FOR UPDATE`, decrypts into a short-lived Buffer, re-encrypts the **same 160-bit seed** under v2 with a fresh 96-bit nonce and account+version authenticated data, zeroes the plaintext buffer, and writes only the cipher envelope plus audit event in one database transaction. It preserves `status`, `enabled_at`, `pending_expires_at`, `last_accepted_step`, failure count, lockout and existing device proof. Invalid keys, wrong key version, malformed reason/request UUID and unprivileged actor all fail without modifying factor or audit. Concurrent operator attempts for the same row allow exactly one change; repeat is `changed:false` without a fabricated audit. Audit includes only actor/target/old/new **key version**, trusted request UUID and reason, never secret, ciphertext, nonce or raw key.

**Security distinction:** re-encrypting the same MFA seed protects encrypted database storage under a new key. It does **not** revoke a compromised TOTP authenticator, recover a lost phone, erase exposed historic backups, replace the seed or grant permission. Those operations need a separate human-reviewed recovery/reset design. The presence of rewrap helpers is **not authorization to access production keys or run mutations**, nor proof that key escrow/rollback is production ready. Unit tests cover versioned AES-GCM AAD, keyring misconfiguration and preserved seed; `bash infra/lab.sh admin-totp-rotation-smoke` uses 2 local Folio `folio_test` DB pools, synthetic superadmin device MFA and real encrypted TOTP records to verify authorization, concurrency, audit, v1-v2 decode and replay invariants. Existing HTTPS smoke additionally exercises opt-in v2 enrollment and 503 on missing/duplicate staged keys. Native test and UI key management remain open.

## Lost-factor review ledger, NOT recovery execution (#30 partial)

The new `0016_admin_mfa_recovery_review.sql` and `admin-mfa-recovery.ts` implement only time-bounded, auditable **two-superadmin MFA-authenticated review** for a lost authenticator. The proposer and approver must be different active MFA-verified superadmins and must not be the target; an existing active target admin TOTP factor is required. PostgreSQL limits one open case per account, explicit pending/approved/cancelled/expired transitions, and a 24-hour validity window. This ledger cannot replace or remove the TOTP seed, clear a replay/lockout counter, issue an MFA proof or change roles. Syntax-checked support reference and dual account actions are **NOT** human identity verification or permission to execute a future reset. No public API/UI/CLI executor was created. Genuine identity verification, human change approval, safe session revocation, recovery enrollment, lost-all-admin recovery and native tests remain blocked. See `docs/47-ADMIN-MFA-RECOVERY-REVIEW.md` and `admin-mfa-recovery-smoke` for tests and limits.

## Paperbound browser factor enrollment form (#30 incremental)

`apps/admin/src/AdminMfaPanel.tsx` adds a TR/EN, responsive Settings flow backed by the gated actual-HTTPS Web login/CSRF and TOTP enroll/confirm/verify/logout routes. **It sends no secret request on insecure HTTP**, displays the authenticator setup key only in temporary React component memory, never stores/copies it to storage/URL/analytics, and clears it after successful enrollment confirmation or screen dismissal. Factor enrollment does not set admin access; fresh second code must succeed for the exact server device session before even reporting proof. Admin catalogs/users remain unavailable without separately authorized CRUD. SSR/browser HTTP tests, bounded strict response validation, Chrome 390px + translations and earlier real NestJS HTTPS PostgreSQL smoke are available. Actual browser HTTPS end-to-end on production infrastructure, safe first-admin bootstrap, lost-factor recovery, key custody, WebAuthn and native QA **remain open**.
