# #30 Internal encrypted admin TOTP verifier (partial V1)

## Operational boundary
The V1 role and session prerequisite is the merged #43 RBAC/MFA gate. The new **internal-only** `@folio/db` functions `beginAdminTotpEnrollment`, `confirmAdminTotpEnrollment`, and `verifyAdminTotpForSession` do not create a public/authenticated HTTP route. They are callable only by a future trusted TLS/CSRF admin controller, which MUST derive the opaque session token from the verified transport and `requestId` from `RequestIdMiddleware`. Never accept an `x-admin-role`, query/body actor, user-provided clock or pasted encryption key. No role or first superadmin is created by TOTP enrollment. HTTPS enrollment/verify UX and independently reviewed initial superadmin bootstrap remain blocked. The code cannot make an admin from an ordinary signed-in account without an existing, nonrevoked DB role.

## Secret protection and validation
- The forward-only `0014_admin_totp_credentials.sql` migration creates an empty `admin_totp_credentials` table; existing user/canonical/content rows are untouched. The pending seed is random 160 bits generated by Node CSPRNG, returned once to its authenticated enrolled-account operator (never logged); it is persisted ONLY as AES-256-GCM ciphertext, unique random 96-bit IV and 128-bit GCM tag. AAD `folio:admin-totp:v1:<user_uuid>` binds ciphertext to that account. Wrong key, swapped user or tampered cipher **fail closed**. DB stores `key_version='v1'` for future controlled rotation. A **32-byte private server key** passed from secure configuration is mandatory; no default, test key or hardcoded production secret. No key is committed. Backups must include separately protected decryption-key recovery, but key rotation/recovery is not yet implemented.
- TOTP is RFC 6238 SHA-1, six digits, 30-second timestep, only current server timestep ±1 accepted. No client-provided date/time, algorithm or seed. Confirmation of a pending enrollment requires a correct TOTP within ten minutes, and **does not mint admin access**. A subsequent *different, previously unused* TOTP code is required for session step-up.
- `last_accepted_step` advances monotonically **inside the same transaction** under `FOR UPDATE` on the factor row. Identical code/time step cannot authorize a second request or device even on separate PostgreSQL pools. Code strings are not stored or audited; the encryption key and raw bearer never enter audit.
- Wrong codes increment a persistent `failed_attempts` counter (five failures block attempts for fifteen minutes), committed **before** a uniform denial is thrown. A cryptographic key/configuration outage does not silently create an MFA bypass. Expired enrollment cannot be confirmed. A pending/active seed cannot be silently replaced, except expired pending enrollment may begin anew.
- A real `verifyAdminTotpForSession` success creates/updates `admin_session_mfa` with the *same* user+session, `method='totp'`, `verified_at` and fifteen-minute expiry in that transaction. `withVerifiedAdminPermission` still checks active email-verified account, unrevoked device, current proof and exact DB role/permission; private book bodies remain forbidden even to superadmin.

## CI evidence and limitations
`packages/db/src/admin-totp-crypto.spec.ts` checks the RFC SHA-1 test vectors, 6-digit replay window and authenticated encryption tamper/account-binding. `packages/db/scripts/admin-totp-smoke.ts` runs only on dedicated loopback Folio `folio_test`: pending-role denial, invalid encryption-key handling, secret-free persisted rows and audit, five wrong attempts lockout, pending confirm, no MFA proof merely from enrollment, two DB pools and two verified devices racing the SAME fresh code (exactly one accepted), proof bound to the winner's session, role revocation and device logout. A time-lock expiry is **simulated only by test fixture DB mutation**; production has no unlock/recovery endpoint. CI invokes `bash infra/lab.sh admin-totp-smoke` between RBAC and role lifecycle tests.

**Not completed:** real secure browser/native factor enrollment and CSRF/CSP flows, controlled deployment and rotation/recovery of the server-only AES key, admin MFA reset/lost device procedure, WebAuthn, first-superadmin bootstrap with human identity/audit verification, production/native device end-to-end QA and #7 dependency release security. Do not claim #30/#43 complete or deploy before these conditions and explicit user approval.
