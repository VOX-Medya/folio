# Folio #26: fail-closed ClamAV stdin-only quarantine scanner (partial)

## Boundaries

`packages/db/src/quarantine-scanner.ts` provides a trusted **internal** `ClamAvStdinScanner` implementing `QuarantineByteScanner`. `LocalStorageAdapter.scanQuarantined` receives a previously persisted, owner-scoped `pending_verify` record, opens its file using `O_NOFOLLOW`, checks inode ownership/mode 0600/hardlink count and streams **the opened descriptor's bytes** into the scanner. It never supplies a private file path, storage key, personal identity or source text to the subprocess arguments. The output is a transient `clean` or `infected` observation bound to an independently streamed SHA-256, exact byte count and unchanged inode/mtime/ctime; the method **never edits media_assets, never changes status from pending_verify, never promotes files or grants publication rights**. Errors (missing scanner, missing definitions, scanner errors, malformed responses, excessive log output, timeout, unread bytes, unsafe inode, hash or size change) deny progress.

Official [ClamAV clamscan](https://docs.clamav.net/manual/Usage/Scanning.html) accepts standard input with `-`; exit 0 is no virus detected, 1 infected and 2 error ([man page](https://manpages.debian.org/bookworm/clamav/clamscan.1.en.html)). The production-default subprocess runs `/usr/bin/clamscan` with no shell, fixed `-` input, `--no-summary --stdout`, `--fail-if-cvd-older-than=3`, `--alert-exceeds-max=yes`, `--alert-encrypted=yes` and bounded file/expanded scan/recursion/time limits. It accepts only exactly `stdin: OK` for clean and a single `stdin: ... FOUND` infection line for positive detection. Exit 0 with warnings, noisy or unknown output is not proof of a clean scan.

The initial scanner limit is **16 MiB**, smaller than the 1 GiB raw quarantine upload limit. Larger assets remain inaccessible/pending until scanner capacity and format coverage are separately validated. Unsafe embedded compression/encrypted artifacts must fail instead of silently skipping unchecked bytes. The 3-day official signature age flag may be unavailable on older ClamAV binaries; unsupported options fail the scan. Production operators must install and update a supported ClamAV engine and verified current signature databases, demonstrate actual-version behavior, and manage scanner CPU/RAM/time budgets before enabling verification. **The current Folio Docker image intentionally does not include ClamAV/signature databases.** No daemon, provider service, network access, production scanner configuration, freshclam updates, or cleanup of private files are activated here.

## Test evidence and explicit limitations

`quarantine-scanner.spec.ts`: synthetic Node child process and real temporary private vault fixtures test clean/infected messages, subprocess errors, malformed output, stderr warnings, excessive stdout, timeouts, missing binary, scan byte-size ceiling, premature clean without data consumption, owner/key forgery, SHA mismatch, symlink, chmod 0640, mutation during scanning. A positive synthetic mock does not constitute malware test coverage.

Separate GitHub Actions job `clamav-native-protocol` installs **real ClamAV binary on an ephemeral Ubuntu runner** and executes `db:clamav-native-smoke` using a locally constructed, harmless MD5 test signature file and two synthetic text payloads. This proves only the scanner CLI protocol and integration, not official signatures, database freshness or antivirus detection of real threats. To avoid falsely claiming signature freshness, **only this synthetic job** omits `--fail-if-cvd-older-than=3`, and uses the synthetic signature database with `--database=...`; production defaults are unchanged. No EICAR malware bytes, real books, user files, or network-fetched signature definitions are required. Both clean and flagged synthetic files remain **pending_verify**.

**Not done / #26 remains open:** real fresh official signature lifecycle, scanner installation and rights isolation on the target Ubuntu machine, full EPUB/PDF archive and semantic validation, audio codec/duration checks, scanner+parser signed evidence, actual atomic verified promotion, authorized media Range/TTL/rights revocation, local/native QA. `#7` release dependency audit remains a hard blocker. A green development CI never authorizes publication, production builds or deployment.
