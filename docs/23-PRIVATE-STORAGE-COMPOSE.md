# Folio V1 private assets: isolated Compose foundation (#26)

Only the **Folio** Docker Compose project `folio_lab` is touched. In `infra/compose.lab.yml`, `folio_lab_private_assets` is a distinct named volume separate from `folio_lab_postgres_data`. No other project's containers, networks, volumes, files or ports are modified. Docker Compose's `storage-init` one-shot container has no network access, uses restricted chown/chmod permissions, assigns the volume root to Node UID/GID `1000:1000`, and enforces `0700` directory access. It does **not** copy data to another service or external endpoint.

The Folio API and optional `jobs` worker both mount the vault at `/opt/folio-private`; the environment variable `FOLIO_PRIVATE_STORAGE_ROOT` names this path. The admin/Vite/Expo web static servers do **not** mount it. The API and worker wait for successful storage initialization before starting. The existing Folio API/DB loopback ports remain unchanged. Docker lab `down` does not delete volumes, and destructive `down -v` or production commands are not added.

GitHub-hosted Ubuntu workflow `.github/workflows/folio-private-vault.yml` (manual trigger or Compose changes in a PR) checks Compose service mount targets and volume namespace, starts the isolated init service and examines actual volume ownership/mode through a read-only ephemeral container. This is an **infrastructure permission acceptance test**, not a server-side upload, malware, full audio codec/duration, per-user quota or authenticated download test.

The companion quarantine-only `LocalStorageAdapter` (#26 PR #80) stages bytes using generated opaque UUIDs with SHA-256 and private file permissions. The private vault path is only a configured server path. It is not itself a public service and no upload/playback route should be activated until trusted auth, DB metadata lifecycle, rights/territory guards and scanner verification exist. #19 and #16 stay blocked for full source/audio import until those conditions are satisfied. No real book or account data is present in GitHub Actions; all tests use ephemeral infrastructure and synthetic fixtures.


## EPUB OCF MIME giriş kontrolü ve gelecekteki storage sınırı (#26 kısmi)

Yerel `StorageAdapter` arayüzünde V1 yalnız `stage` ve `inspectQuarantined` işlevlerini sunar. İkisi de `pending_verify` sınırında kalır; **public read, URI, signed download veya verified promote bulunmaz**. Local implementasyon `LocalStorageAdapter` bu arayüze uyar. S3/remote provider import veya yeni servis kullanılmaz.

W3C [EPUB 3.4 OCF 4.3.3](https://www.w3.org/TR/epub-34/) ilk ZIP üyesinin `mimetype` ve gövdesinin tam ASCII `application/epub+zip` olmasını; üyenin sıkıştırılmamış, şifrelenmemiş, ZIP extra field olmadan yazılmasını zorunlu kılar. `LocalStorageAdapter.stage` ilk **58 baytlık local file header** üzerinden bunu en çok 64 baytlık bellek sınırı içinde, parçalı stream'den deterministik doğrular. Salt `PK\x03\x04` imzası taşıyan sıradan ZIP, yanlış ilk ad, şifreleme/descriptor, sıkıştırma, ZIP ekstra alan, yanıltıcı boyut, MIME boşluk/BOM/yanlış değer ve yetersiz header reddedilir; kısmi staging dosyası temizlenir.

**Bu kontrol sadece media type admission'dır, EPUB parser değildir:** ZIP central directory ve tüm girişleri, zip-slip/zip-bomb limitleri, DRM, HTML/XML sanitizasyonu, tutarlı kaynak sırası, içerik kalitesi, hak kanıtı ve malware taraması doğrulanmış sayılmaz. Sentetik olumlu bir OCF ilk-header fixture bile **`pending_verify`** olur, yayımlanmaz/ayrıştırılmaz. EPUB/PDF bozuk içeriklerini OCR veya AI ile onarma akışı yoktur. Gerçek scanner veya semantik parser entegre edilmeden verified geçişi ve API indirme kapalıdır. `local-storage.spec.ts` UTF-8/EPUB ZIP spoof negatif testlerini GitHub Actions `pnpm check` altında çalıştırır.
