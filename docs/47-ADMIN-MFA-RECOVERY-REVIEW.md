# #30 V1 admin MFA lost-factor recovery REVIEW (partial, internal-only)

## Safety boundary

This change does **not** reset a TOTP authenticator, decrypt or expose a seed, waive multi-factor authentication, issue an administrator session proof, grant a role, or manufacture a recovery code. It only records a **review request** for a person who reports a lost/compromised factor. The `approved` state is a record of two independent, currently MFA-authenticated and database-authorized **superadmin account actions**. It is **not independent real-world identity attestation, permission to execute a reset, or verified ownership of a human ticket**. Those external controls require review and human approval before any production-facing recovery execution exists.

No public admin endpoint, self-service lost-device button, command-line reset, break-glass password bypass, default superadmin or automation was added. Without at least two independent functioning superadmin factors, this internal workflow cannot be approved. That lockout is intentional and the out-of-band governance path has to be designed and authorized separately.

## Data contract

Forward-only `0016_admin_mfa_recovery_review.sql` creates the initially empty `admin_mfa_recovery_requests` table. It stores a random UUID, target account ID, proposer/approver account IDs, a non-sensitive `REC-` prefixed support reference, a bounded rationale, creation and expiration timestamps, and status `pending|approved|cancelled|expired`. A PostgreSQL partial unique index permits **one pending or approved request per target**. SQL CHECK constraints prohibit the proposer or approver being the target, prohibit the proposer approving their own case, require an approver and timestamp for approved, reject fake approved rows lacking those fields, and bound expiration to **24 hours** after creation. Closed rows stay as audit evidence rather than being overwritten.

The support reference is a manually supplied syntax-checked correlation ID, **not evidence of a real case or identity verification**. The rationale and reference must never contain passwords, OTP codes, personally sensitive records, encryption keys or bearer tokens. The data contract does not persist any TOTP seed/ciphertext or include recovery material.

## Internal-only domain operations

- `proposeAdminMfaRecoveryReview(db,bearer,targetUserId,supportReference,reason,trustedRequestId)`: requires a non-revoked, email-verified DB superadmin, valid **same-device MFA**, and `users:support` permission. Proposer != target. Target must be active/email-verified, have a non-revoked admin membership and a previously activated TOTP factor. Validates UUIDs, bounded rationale and support reference. Opening one request creates exactly one audit event with actor, case, target, reference, reason and server-owned request UUID. A duplicate matching reference is a no-op; a different reference cannot silently replace a live case.
- `approveAdminMfaRecoveryReview(db,bearer,reviewId,supportReference,reason,trustedRequestId)`: requires a **different** currently MFA-verified superadmin who is not the subject. Requires matching case reference and revalidates the target account, role and factor; case row is locked `FOR UPDATE`. Exactly one eligible reviewer wins a concurrency race. A second attempt does not create a second approval/audit. Approval stays a **review-only** state and cannot alter the MFA factor.
- `cancelAdminMfaRecoveryReview(db,bearer,reviewId,reason,trustedRequestId)`: a verified superadmin can cancel pending or approved reviews without touching the factor. Cancellation is monotonic/idempotent, preserving the original approval metadata and audit.
- Expired cases are closed when a verified operator next touches the relevant review, with an audited `expired` transition; this is **lazy expiry**, not a background scheduler. A new request may then open under a different case reference. The 24-hour deadline still blocks old-case approval regardless of whether a cleanup job has run. No live watchdog/notifications or automatic re-enrollment are claimed.

All privileged mutations execute inside `withVerifiedAdminPermission` with the existing account, device session, MFA proof and role locks; the proposal additionally validates target account/role/TOTP factor under row share locks. The target case is then locked before approval/cancellation, and all status changes and `audit_events` write atomically in the same PostgreSQL transaction. Authorization cannot be satisfied by HTTP headers such as `x-admin-role` or caller-selected account ID. No new HTTP route has been mounted.

## Evidence and outstanding work

`packages/db/scripts/admin-mfa-recovery-smoke.ts` is restricted to the dedicated Folio `folio_test` database on loopback. It creates only **synthetic** verified test accounts and roles, activates real encrypted TOTP factors, and obtains genuine RFC 6238 proofs for three independent superadmin test sessions. It checks missing MFA, self-recovery, no target factor, malformed request fields, duplicate/proposer self-approval, unrelated user denial, **two-pool concurrent independent approval** (one winner/one audit), cancellation idempotence, concurrent proposals (one winner), 24-hour expiry and reopening, DB CHECK constraints, audit omissions for all secrets, and **exactly unchanged** target TOTP row and no new target MFA proof.

The following are **NOT implemented**: authenticated in-product human support verification, actual customer ticket linkage, secure review UI, secure separate out-of-band identity attestations, independent operation approval, reset/execution of factor or revocation of historic device proofs, lost-key recovery, verified full backup and rollback, first-superadmin bootstrap, native device testing, release dependency fixes. There is deliberately **no reset executor**. When recovery execution is later designed, it will require separate approvals, atomic device-proof revocation, fresh seed re-enrollment with strictly limited transport, non-replayable user consent, rate limiting, audit, recovery abuse controls, and full negative integration tests. Do not interpret this review feature as production-ready MFA recovery or close #30/#43.
